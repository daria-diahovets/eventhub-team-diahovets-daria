## 1. Мета роботи

Підняти каркас монорепо EventHub і замкнути перший наскрізний цикл **специфікація → згенеровані типи → типізований запит із фронтенду**, не написавши жодного рядка бекенду.

Після виконання студент вміє:

- організувати багатопакетний репозиторій на pnpm workspaces і Turborepo;
- читати й будувати граф залежностей задач, розуміти, що саме інвалідує кеш;
- описати ендпоїнт в OpenAPI 3.1 разом із параметрами, схемою відповіді та помилками;
- згенерувати з цієї специфікації типи TypeScript і використати їх на клієнті;
- підняти мок-сервер, який дозволяє фронтенду працювати до появи бекенду;
- задокументувати архітектурне рішення у форматі ADR.

### Головна ідея, яку перевіряє ця робота

Фронтенд і бекенд не домовляються в чаті. Вони домовляються файлом, який лежить у репозиторії, читається обома, і з якого машина сама виводить типи.

Якщо в кінці лабораторної ви написали хоча б один інтерфейс запиту чи відповіді руками — робота виконана неправильно, навіть якщо все працює. Рукописний тип — це друга версія правди. Дві версії правди завжди рано чи пізно розходяться, і виявляється це в найгірший момент.

### Правила роботи з методичним посібником

Кожен крок має три частини:

- **Що робимо** — команди й код, які треба виконати.
- **Чому саме так** — пояснення рішень. Це не «додаткова інформація»: питання звідси ставитимуть на захисті.
- **Контрольна точка** — перевірка, що крок справді завершено.

Не переходьте до наступного кроку, поки контрольна точка не пройдена. Помилка, зроблена на кроці 2, виявиться аж на кроці 5, і шукати її ви будете вдвічі довше, ніж робили обидва кроки.

## 2. Передумови

Перевірте перед початком. Якщо якоїсь позиції немає — ставте зараз, це займе 5 хвилин і зекономить півгодини потім.

```bash
node --version    # v24.20.0 або новіше в лінії 24
pnpm --version    # 11.x
git --version
```

> **Чому саме 24.20, а не «щось новіше».** Верхня межа: непарні лінії Node (23, 25, 27) — це Current-гілка з короткою підтримкою, на ній частина залежностей видає попередження на кшталт `DeprecationWarning: url.parse()`, і ви витрачаєте час на діагностику того, що не є вашою проблемою.
>
> Нижня межа взята не зі стелі: `@stoplight/prism-cli` оголошує `engines.node: >=24.18.0`. Через це лінія 22 не підходить узагалі, хоча вона теж LTS. Це загальне правило, а не особливість нашого проєкту: **нижня межа Node — це максимум із ваших потреб і вимог усіх залежностей**. Ви можете її лише підняти; один пакет у дереві диктує мінімум усьому проєкту.
>
> У корені лежать `.nvmrc` і `.node-version` зі значенням `24.20.0`.
>
> Важливо: ці файли **нічого не встановлюють і не перемикають**. Це текстові файли з числом, які читає менеджер версій, коли ви явно даєте йому команду.

**Як перемкнути версію**

| Інструмент | Команда | Читає файл версії |
|---|---|---|
| fnm (рекомендовано, усі ОС) | `fnm install && fnm use` | так |
| nvm (Linux, macOS) | `nvm install && nvm use` | так |
| Volta | перемикає сам | так |
| **nvm-windows** | `nvm install 24.20.0`, далі `nvm use 24.20.0` | **ні** |

**Якщо ви на Windows, зверніть увагу на останній рядок.** nvm-windows — це окремий проєкт, не порт оригінального nvm: він не читає `.nvmrc` і вимагає повний номер версії, тож ані `nvm use` без аргументу, ані `nvm install 24` там не працюють.

Простіше поставити fnm — він крос-платформний, швидкий і читає ті самі файли, що й nvm:

```powershell
winget install Schniz.fnm
fnm install
fnm use
node -v          # має показати v24.20.0
```

`fnm use` діє лише в поточному терміналі. Щоб версія перемикалась автоматично при вході в папку, додайте в профіль PowerShell (`notepad $PROFILE`) рядок:

```powershell
fnm env --use-on-cd | Out-String | Invoke-Expression
```

Без цього кожен новий термінал повертатиметься до системного Node, і помилка `ERR_PNPM_UNSUPPORTED_ENGINE` з'являтиметься знову — на вигляд випадково.

Якщо pnpm немає:

```bash
corepack enable
corepack prepare pnpm@11 --activate
```

> **Що таке corepack.** Це вбудований у Node.js менеджер менеджерів пакетів. Він читає поле `packageManager` у `package.json` і сам ставить потрібну версію pnpm. Завдяки цьому вся команда працює однією версією інструмента, і не буває ситуації «у мене працює, а в тебе lock-файл інший».
>
> Версія в `packageManager` записується точним числом, без діапазону — це вимога corepack. Якщо `pnpm -v` показує щось інше, ніж записано в корені, corepack сам підтягне потрібну при першій команді.

### Термінал

**Усі команди в методичці записані для Bash.** На Linux і macOS це термінал за замовчуванням. На Windows — Git Bash (ставиться разом із Git) або WSL2.

Це не вимога до вашого смаку, а спосіб уникнути витраченого часу: у cmd і PowerShell частина команд поводиться інакше або не існує взагалі. Наприклад, `echo "" >> file.txt` у Bash додає порожній рядок, а в cmd дописує в файл два символи лапок — і дослід із кешем на кроці 1 покаже не те, що мав.

### Якщо ви в VS Code

Сказати «працюйте в Git Bash» замало: VS Code на Windows відкриває вбудований термінал у PowerShell, навіть коли Git Bash встановлений.

Цього не треба налаштовувати вручну — у репозиторії є `.vscode/settings.json`, який застосовується автоматично при відкритті папки проєкту:

```json
"terminal.integrated.defaultProfile.windows": "Git Bash"
```

Якщо термінал усе одно відкривається в PowerShell — ви відкрили у VS Code не корінь репозиторію, а якусь підпапку. Відкрийте папку `eventhub` цілком.

**Друге, що робить цей файл, і чому це важливіше, ніж здається:**

```json
"typescript.tsdk": "node_modules/typescript/lib"
```

Без цього рядка VS Code перевіряє код **власним** компілятором TypeScript, вбудованим у редактор, а не тим, що лежить у `node_modules`. У нас закріплена версія 5.9.3, у редакторі може бути інша — і ви отримаєте класичне «у редакторі все зелено, а `pnpm typecheck` падає» або навпаки.

Перевірте: відкрийте будь-який `.ts`-файл і подивіться на версію TypeScript у рядку стану внизу. Якщо там не 5.9.3 — натисніть на неї та оберіть **Use Workspace Version**.

При першому відкритті VS Code запропонує рекомендовані розширення зі списку `.vscode/extensions.json` — погодьтесь. Одне з них перевіряє `openapi.yaml` просто в редакторі, тож на кроці 2 ви побачите помилки специфікації, не відкриваючи Swagger Editor.

### PowerShell: відповідники команд

Якщо все-таки працюєте в PowerShell, ось відповідники того, що трапляється в методичці:

| Дія | Bash | PowerShell |
|---|---|---|
| перші рядки виводу | `… \| head -40` | `… \| Select-Object -First 40` |
| дописати рядок у файл | `echo "текст" >> file` | `Add-Content file "текст"` |
| видалити папку рекурсивно | `rm -rf node_modules` | `Remove-Item -Recurse -Force node_modules` |
| показати заголовки відповіді | `curl -i URL` | `curl.exe -i URL` |

Останній рядок вартий уваги: у Windows PowerShell 5.1 `curl` — це псевдонім для `Invoke-WebRequest` з іншим набором прапорців. Пишіть `curl.exe` явно, щоб отримати саме curl.

**Windows: закінчення рядків.** Одразу налаштуйте:

```bash
git config --global core.autocrlf input
```

> **Навіщо.** Windows завершує рядок парою CRLF, Unix — одним LF. Без цієї настройки git при кожному коміті мінятиме закінчення в усіх файлах, і ваш PR виглядатиме як «змінено 300 файлів» замість «змінено 3». Рев'ювер у такому дифі не побачить нічого.


Чого ще немає і що ви створите самі: `pnpm-workspace.yaml`, кореневий `package.json`, `turbo.json`, увесь пакет `packages/contracts`.

### Чому саме так

**Чому монорепо, а не окремий репозиторій на кожен сервіс.**

Головний аргумент — **атомарність зміни**. Уявіть, що ви додали в подію поле `ageRating`. У монорепо це один PR: специфікація, бекенд і фронтенд змінюються разом, CI перевіряє їх разом, рев'ювер бачить усю картину. У семи репозиторіях це три PR у трьох місцях, які треба змерджити в правильному порядку, і надія на те, що ніхто не забуде третій.

Ціна монорепо теж є, і її треба знати: репозиторій росте, збірка «всього» стає повільною, права доступу однакові для всіх папок. Перше й друге лікує саме Turborepo, третє — ні. Для навчального проєкту й для команд до 50 людей монорепо майже завжди виграє.

### Розподіл ролей у команді

Ролі на сьогодні фіксуються в описі PR і міняються наступного тижня.

- **Автор** — пише код, робить коміти.
- **Рев'ювер** — не пише в цю гілку; читає діф, ставить питання, приймає роботу за критеріями з розділу 12.
- **Інтегратор** (у командах із трьох) — тримає README актуальним, перевіряє, що інструкція із README справді працює на чистій машині.

> **Чому рев'ювер не пише код.** Спокуса «швидше сам поправлю» вбиває сенс рев'ю. Завдання рев'ювера — зрозуміти чужий код настільки, щоб задати про нього змістовне питання. Це окрема навичка, і вона тренується лише забороною правити самому.

## 5. Крок 1. Монорепо

### 5.1. Оголошуємо workspace

Створіть у корені `pnpm-workspace.yaml`:

```yaml
packages:
  - "apps/*"
  - "packages/*"

engineStrict: true

allowBuilds:
  esbuild: true          # потрібен Vite для збірки фронтенду
  "@scarf/scarf": false  # телеметрія, збирати нічого
```

> **Що дає `packages`.** Тепер pnpm знає, що репозиторій складається з кількох пакетів. Він ставить залежності один раз у корені, а всередині пакетів створює символьні посилання. Головне — пакети можуть залежати один від одного за іменем, а не за відносним шляхом: `@eventhub/contracts` замість `../../packages/contracts`.
>
> **Чому `pnpm-workspace.yaml`, а не `package.json`.** Починаючи з pnpm 11, усі налаштування pnpm живуть тут; поле `"pnpm"` у `package.json` більше не читається. Якщо натрапите на старі інструкції з `"pnpm": { ... }` — вони застаріли, і pnpm скаже про це попередженням.
>
> **`engineStrict: true`** перетворює попередження про невідповідну версію Node на помилку встановлення. Без нього поле `engines` — лише побажання, і ви цілком можете півсеместру працювати на версії, якої не планували.

### Що таке `allowBuilds` і чому це не формальність

Пакет може містити `postinstall` — скрипт, який виконується під час встановлення. Це легальний механізм: `esbuild` так розпаковує свій бінарник під вашу платформу. Але це ж і найзручніший вектор атаки на ланцюг постачання: досить скомпрометувати один популярний пакет, і його `postinstall` виконається на машині кожного, хто оновить залежності.

Тому pnpm за замовчуванням **не виконує** ці скрипти, доки ви явно не вирішите по кожному пакету:

- `esbuild: true` — знаємо, навіщо, дозволяємо;
- `"@scarf/scarf": false` — це телеметрія, збирати нема чого, забороняємо.

Пакет, якого немає в списку, вважається нерозглянутим. Установка при цьому **падає** з `ERR_PNPM_IGNORED_BUILDS` — не попереджає, а саме падає з ненульовим кодом виходу.

Це навмисно незручно. Рішення «дозволити виконання чужого коду на своїй машині» має бути свідомим і зафіксованим у репозиторії, де його побачить рев'ювер.

Якщо у вас з'явиться новий пакет зі скриптом, pnpm сам допише його в `pnpm-workspace.yaml` із заглушкою — вам залишиться поставити `true` або `false`. Приймати рішення наосліп не варто: подивіться, що саме робить `postinstall` цього пакета.

> До цієї теми ми повернемось у тижні 15, коли говоритимемо про безпеку ланцюга постачання. Тоді ж стане зрозуміло, чому три застарілі пакети всередині Prism, яких ви не встановлювали, — це не дрібниця.

### 5.2. Кореневий package.json

```json
{
  "name": "eventhub",
  "private": true,
  "packageManager": "pnpm@11.24.0",
  "engines": { "node": "^24.20.0" },
  "scripts": {
    "dev": "turbo run dev",
    "build": "turbo run build",
    "lint": "turbo run lint",
    "typecheck": "turbo run typecheck",
    "contracts": "turbo run build --filter=@eventhub/contracts",
    "mock": "prism mock packages/contracts/openapi.yaml --port 4010"
  },
  "devDependencies": {
    "@stoplight/prism-cli": "^5.16.0",
    "prettier": "^3.4.0",
    "turbo": "^2.10.0",
    "typescript": "5.9.3"
  }
}
```

> **`"private": true`** тут не формальність. Без нього pnpm вважатиме корінь публікованим пакетом і сваритиметься на кожній команді. Публікувати корінь монорепо не має сенсу — це контейнер, а не бібліотека.
>
> **`"engines"` — чому `^24.20.0`, а не `>=22`.** Запис `>=22` пропускає будь-що новіше, включно з Node 23, 25 і 27 — а це Current-гілка, не призначена для тривалої роботи. Каретка обмежує діапазон однією мажорною лінією, тож усе за межами 24.x відсікається за побудовою.
>
> Нижня межа `24.20.0` продиктована залежністю: Prism вимагає `>=24.18.0`. Тому лінія 22 виключена, хоча формально теж LTS.
>
> Саме поле `engines` лише **попереджає**. Щоб перевірка стала блокуючою, у `pnpm-workspace.yaml` увімкнено `engineStrict: true` — тоді невідповідна версія дає `ERR_PNPM_UNSUPPORTED_ENGINE` і встановлення зупиняється.
>
> Ця ж інформація в тижні 13 потрапить у налаштування CI, а в тижні 12 — у базовий образ Docker. Один факт, записаний в одному місці.
>
> **`"typescript": "5.9.3"` — без каретки.** Це навмисно. TypeScript не дотримується semver у звичному сенсі: будь-який мінорний реліз може додати перевірку, яка зламає збірку, що вчора проходила. У монорепо компілятор фіксують точною версією, інакше двоє учасників команди з різницею в тиждень між `pnpm install` отримають різні помилки на однаковому коді.


### Усі команди запускаються з кореня

Скрипти `build`, `mock`, `contracts` живуть у **кореневому** `package.json`. Якщо запустити їх із `apps/web`, буде:

```
ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL  Command "mock" not found
```

З підпапки те саме працює як `pnpm -w mock` (`-w` означає «у корені воркспейса»).

Другий, підступніший симптом тієї самої помилки: `pnpm build` з `apps/web` запускає `vite build` напряму, минаючи Turborepo. Збірка проходить, але збирається один пакет — і досліди з кешем нижче не показують нічого.

### 5.3. turbo.json

Це найважливіший файл кроку. Прочитайте пояснення нижче **до** того, як копіювати.

```json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", "build/**", "src/generated/**"]
    },
    "typecheck": {
      "dependsOn": ["^build"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "lint": {}
  }
}
```

### Чому саме так

**Що взагалі робить Turborepo.** Він не збирає код — збирають Vite, Nest і TypeScript. Turborepo лише вирішує **в якому порядку** запускати задачі та **чи можна не запускати їх узагалі**, узявши результат із кешу.

**`dependsOn: ["^build"]` — що означає дашка.**

Це топологічна залежність: «спершу виконай задачу `build` в усіх пакетах, від яких я залежу». Без дашки (`"build"`) це була б залежність усередині того самого пакета.

Різниця принципова:

```
"dependsOn": ["^build"]  → спершу contracts#build, потім web#build
"dependsOn": ["build"]   → задача в цьому ж пакеті (для build — безглуздо)
```

**Як Turborepo вирішує, чи брати з кешу.**

Для кожної задачі рахується хеш. У нього входять:

- вміст усіх файлів пакета, які **відстежує git** (ігноровані через `.gitignore` — не входять);
- сама команда з `scripts`;
- хеші задач, від яких ця задача залежить;
- змінні оточення, оголошені в `env`.

Збігся хеш — задача не запускається, а її `outputs` розпаковуються з кешу. Не збігся — запуск.

**Чому `outputs` обов'язкові.** Це перелік того, що задача виробляє. Якщо його не вказати, Turborepo порахує хеш, але зберігати йому буде нічого — і при наступному запуску він змушений буде виконати задачу заново. Класична помилка «кеш чомусь не працює» майже завжди означає забуті `outputs`.

**Чому тут немає окремої задачі `generate`.**

Спокусливо оголосити в пакеті `contracts` задачу `generate` і написати в `build` фронтенду `dependsOn: ["^build", "generate"]`. Так роблять часто — і це **не працює**:

- `^build` шукає задачу `build` у залежностях. Якщо в `contracts` є тільки `generate`, ребро графа просто не утвориться — Turborepo мовчки пропускає задачі, яких у пакеті немає.
- `generate` без дашки означає `web#generate`, тобто задачу в тому самому пакеті. Її теж не існує.

Підсумок: хеш `web#build` нічого не знає про `openapi.yaml`, і зміна контракту не інвалідує фронтенд. Помилка тиха — усе «працює», просто кеш бреше.

Тому ми називаємо генерацію типів `build` у пакеті `contracts`. Це ще й чесніше по суті: **згенерувати типи — це і є зібрати цей пакет**, іншого артефакту в нього немає.

**Граф, який має вийти:**

```
   contracts#build          ← читає openapi.yaml, пише src/generated/
        │
        ├──────────────► web#build
        │                web#typecheck
        │
        └──────────────► api-gateway#build      (з тижня 2)
```

### 6.3. Чому саме так — розберіть у команді

Це не риторичні питання; відповіді знадобляться на захисті.

**Чому `Money` — це об'єкт із цілим числом, а не `number`?**

Бо `0.1 + 0.2` у подвійній точності не дорівнює `0.3`. Числа з рухомою комою зберігаються у двійковій системі, а `0.1` у ній — нескінченний періодичний дріб, як `1/3` у десятковій. Похибка мікроскопічна, але при підсумовуванні тисяч замовлень стає видимою у звіті.

Тому гроші зберігаються **в мінімальних одиницях цілим числом** — завжди, в усіх системах, де вони справді гроші. 250 гривень — це `25000` копійок.

Валюта поруч із сумою потрібна тому, що в тижні 8 з'явиться Stripe, який працює саме так: `amount` і `currency` окремими полями. Число без валюти — це не сума грошей, а просто число.

**Чому `nextCursor` має тип `[string, "null"]`, а не просто `string`?**

Бо `null` — легальне значення (сторінок більше немає), і фронтенд мусить його обробити.

У OpenAPI 3.1 nullable виражається саме об'єднанням типів. Синтаксис `nullable: true` — зі старої версії 3.0, у 3.1 він не працює: версію 3.1 привели у відповідність до JSON Schema, де такого ключа немає. Це найчастіша помилка при переході між версіями.

Згенерований тип буде `string | null`, і TypeScript змусить це врахувати.

**Чому `availableSeats` є в `required`, а `description` — ні?**

`required` в OpenAPI означає «сервер гарантує наявність цього поля **завжди**», а не «поле важливе». Усе, чого немає в `required`, генератор зробить необов'язковим (`description?: string`), і компілятор змусить фронтенд перевіряти наявність.

Спокуса позначити все обов'язковим закінчується падінням на першому ж записі, де поле порожнє. Спокуса не позначати нічого — купою зайвих перевірок у коді. Ставте в `required` рівно те, що бекенд справді гарантує.

**Чому курсор, а не `page` і `offset`?**

Каталог сортується за датою події. Організатори додають події постійно. Уявіть: користувач отримав сторінку 1 (події 1–20), у цей момент додалася нова подія, що потрапляє на початок списку. Користувач просить сторінку 2 — тобто `OFFSET 20` — і бачить подію, яку вже бачив на першій сторінці, бо все зсунулось на одну позицію.

Курсор — це закодована позиція в сортуванні (`startsAt` плюс `id` для однозначності). Запит «дай наступні 20 після цієї позиції» дає стабільний результат незалежно від вставок.

Ціна: не можна перейти «на сторінку 7», бо номерів сторінок більше не існує. Для стрічки подій це прийнятно, для адмінської таблиці — часто ні. Саме це рішення ви й опишете в ADR на кроці 6.

**Навіщо приклади?**

Prism на кроці 4 віддаватиме саме ці дані. Без прикладів мок-сервер згенерує формально валідні рядки на кшталт `"string"` — з якими неможливо оцінити верстку.

**Три різні ключі з назвою «example» — не плутайте їх**

Це місце в OpenAPI 3.1 плутає майже всіх, і редактор Swagger попереджає саме про нього.

| Де | Правильний ключ | Формат |
|---|---|---|
| Усередині схеми (`schema:`) | `examples` | **масив** значень |
| У Media Type (поруч зі `schema:` у `content:`) | `examples` | **мапа** імен → об'єкт із полем `value` |
| У Parameter Object | `example` або `examples` | одне значення / мапа |

Ключ `example` (однина) усередині схеми **застарілий**. Причина історична: у версії 3.1 схеми привели у відповідність до JSON Schema 2020-12, а там ключове слово називається `examples` і приймає масив. Редактор на нього скаржиться:

```
property "example" is deprecated, use "examples" instead
```

А якщо просто перейменувати, не змінивши формат — отримаєте другу помилку:

```
examples must be an array
```

У нашій специфікації всі приклади винесені на рівень Media Type, у мапу з іменами. Так вони не дублюються в кожній схемі, а Prism отримує повноцінну відповідь замість зібраної по шматках. Приклад для параметра `city` лежить у його схемі як `examples: [Вінниця]` — масив із одного елемента.

**Навіщо два приклади для `/events`**

`filled` і `empty` — це два стани, які фронтенд мусить обробити по-різному. Порожній каталог не помилка, і показувати на ньому спінер або «щось пішло не так» неправильно. Маючи обидва приклади в контракті, ви можете перевірити верстку обох станів ще до появи бекенду — як саме, показано на кроці 4.

**Навіщо `operationId`?**

Це ім'я операції, з якого генератори роблять ім'я функції в клієнті. Має бути унікальним у межах документа. Якщо його не задати, генератор вигадає ім'я з методу й шляху — і воно зміниться, щойно ви переназвете шлях.

### Контрольна точка 2

Якщо ви встановили рекомендовані розширення, помилки специфікації видно прямо в редакторі — у вкладці Problems не має бути жодної для `openapi.yaml`.

Додатково варто подивитись на специфікацію як на документацію: відкрийте [editor-next.swagger.io](https://editor-next.swagger.io) і вставте туди файл. Помилок валідації бути не повинно, а в правій панелі мають з'явитись обидва ендпоїнти з розкритими схемами — приблизно так їх побачить той, хто інтегруватиметься з вашим API.

Додайте `packages/contracts/src/index.ts`:

```ts
// Публічне обличчя пакета. Усі інші пакети імпортують типи звідси,
// а не з ./generated напряму — так шлях до згенерованого файлу
// лишається деталлю реалізації, яку можна змінити без правок у споживачах.

export type { paths, components } from "./generated/schema";

import type { components } from "./generated/schema";

// Зручні псевдоніми: у компонентах пишемо Event, а не
// components["schemas"]["Event"] — читабельніше і коротше.
export type Event = components["schemas"]["Event"];
export type EventPage = components["schemas"]["EventPage"];
export type VenueSummary = components["schemas"]["VenueSummary"];
export type Money = components["schemas"]["Money"];
export type Problem = components["schemas"]["Problem"];
```

### Чому згенероване не комітиться

Це рішення, яке треба вміти пояснити.

Згенерований файл — похідна від специфікації, як `dist/` від вихідників. Якщо тримати його в git, з'являється можливість стану, коли файл не відповідає специфікації: хтось змінив YAML і забув перегенерувати. Рев'ювер такої розбіжності не побачить — діф виглядатиме цілком нормально.

Натомість генерація виконується перед типізацією і в CI, і локально. Невідповідність одразу ламає збірку.

Є й додатковий ефект: `src/generated/` у `.gitignore` означає, що Turborepo **не бере ці файли у вхідний хеш** — він ігнорує те, що ігнорує git. Тому згенеровані типи не «бруднять» хеші й не спричиняють хибних інвалідацій. Але саме тому в задачі обов'язково має бути `outputs` — інакше відновлювати з кешу буде нічого.

Протилежна практика (комітити згенероване) теж існує і має аргументи — насамперед незалежність від інструментів під час збірки й можливість побачити зміну API прямо в дифі PR. Це доречна тема для другого ADR, якщо у вас лишиться час.

### Контрольна точка 3

У будь-якому файлі всередині `packages/contracts` напишіть тимчасово:

```ts
import type { Event } from "./index";
const e: Event = { id: "x" };   // має підсвітитись помилкою
```

Помилка компілятора про відсутні обов'язкові поля означає, що типи справді працюють. Після перевірки рядок приберіть.

## 8. Крок 4. Мок-сервер

### Що робимо

```bash
pnpm mock
```

Залиште цей термінал відкритим. У другому:

```bash
curl -i "http://127.0.0.1:4010/events"
```

Ви маєте отримати статус `200 OK` і дві події з прикладу `filled`.

Тепер те саме з фільтром за містом:

```bash
curl -G --data-urlencode "city=Вінниця" "http://127.0.0.1:4010/events"
```

> **Чому не просто `?city=Вінниця`.** У рядку запиту дозволені лише ASCII-символи; усе інше має бути закодоване у відсотковій нотації (`%D0%92%D1%96%D0%BD...`). Якщо вписати кирилицю напряму, термінал відправить її в кодуванні своєї консолі — у Git Bash на Windows це часто CP1251, а не UTF-8. Prism отримає послідовність, яку не може розібрати, і **обірве з'єднання без відповіді**: curl покаже `0` отриманих байтів і жодного повідомлення про помилку.
>
> `-G --data-urlencode` кодує значення правильно й переносить його в query. Це загальний прийом для будь-яких не-ASCII параметрів, а не костур для цього конкретного випадку.
>
> **Чому `127.0.0.1`, а не `localhost`.** На Windows `localhost` часто резолвиться спершу в IPv6-адресу `::1`, а Prism слухає `127.0.0.1`. Симптом такий самий — тиша замість відповіді. У браузері це не проявляється, у curl проявляється регулярно.

Тепер перемкніть відповідь на другий приклад:

```bash
curl -H "Prefer: example=empty" "http://127.0.0.1:4010/events"
```

Prism віддасть порожній каталог. Заголовок `Prefer` — його штатний механізм вибору серед іменованих прикладів; саме тому ми задавали їх мапою, а не одним значенням.

Це знадобиться вам на кроці 5: перевірити, що фронтенд коректно показує порожній стан, можна без жодних змін у коді — просто інший заголовок запиту.

Перевірте також помилку:

```bash
curl -i "http://127.0.0.1:4010/events?limit=999"
```

### Що Prism робить і чого не робить

Перш ніж рухатись далі, зафіксуйте межу — інакше на кроці 5 ви шукатимете помилку там, де її немає.

| Prism уміє | Prism не вміє |
|---|---|
| перевіряти запит проти специфікації | фільтрувати, сортувати, шукати |
| віддавати приклади з контракту | зберігати стан між запитами |
| обирати серед іменованих прикладів (`Prefer`) | рахувати щось із даних |
| генерувати випадкові дані за схемою (`--dynamic`) | будь-яку бізнес-логіку |

**Практичний наслідок: фільтр не працює — і не повинен.**

```bash
curl -G --data-urlencode "city=Львів" "http://127.0.0.1:4010/events"
```

Ви отримаєте ті самі дві вінницькі події. Мок-сервер не має ані бази, ані коду, який щось відбирає: він віддає приклад, записаний у контракті, незалежно від параметрів.

Специфікація **оголошує**, що параметр `city` існує й має тип `string`. Що з ним робити — предмет реалізації. Вона з'явиться в тижні 2 (NestJS), а справжня фільтрація за базою — у тижні 3.

Так само неоголошені параметри (`?name=щось`) Prism просто ігнорує: він перевіряє те, що описано, а не забороняє все інше.

**А ось це працює:**

```bash
curl -i "http://127.0.0.1:4010/events?limit=999"
```

400, бо в схемі стоїть `maximum: 50`. Різниця принципова: перевірка параметра описана в контракті, фільтрація — ні.

> Запам'ятайте формулювання: мок відповідає на питання **«чи правильної форми ваш контракт»**, а не «чи правильно працює ваша логіка». Плутанина між цими двома питаннями — найчастіша причина хибної довіри до тестів на моках.

### Чому це важливіше, ніж здається

Prism не просто віддає фікстури. Він **валідує запит проти специфікації** і на `limit=999` має відповісти статусом 400 — бо в схемі стоїть `maximum: 50`.

Це означає дві речі:

1. Мок-сервер змушує вас дотримуватись власного контракту ще до появи бекенду. Якщо ваш опис параметрів неповний, ця перевірка нічого не зловить — і ви дізнаєтесь про дірку в контракті лише в тижні 2.
2. Фронтенд, написаний проти Prism, автоматично написаний проти специфікації. Коли в тижні 2 з'явиться справжній бекенд, переключення буде зміною одного `VITE_API_URL`.

**Чому мок-сервер узагалі потрібен.** У команді з двох людей один пише бекенд, другий — фронтенд. Без мока другий чекає на першого. З моком обидва починають одночасно з першої хвилини — і це не «зручність», а головна практична вигода підходу design-first.

### Контрольна точка 4

Обидва ендпоїнти відповідають осмисленими даними, `Prefer: example=empty` перемикає відповідь на порожній каталог, некоректний запит дає 400 із тілом `application/problem+json`.

## 9. Крок 5. Типізований запит із фронтенду

### 9.1. Підключення контракту

```bash
cd apps/web
pnpm add "@eventhub/contracts@workspace:*"
pnpm add openapi-fetch
cd ../..
```

> **`workspace:*`** каже pnpm брати пакет із цього ж репозиторію, а не з реєстру npm. Зірочка означає «будь-яка версія з робочої області» — версії всередині монорепо ми не відстежуємо, бо всі пакети завжди в одному стані.
>
> Подивіться в `apps/web/node_modules/@eventhub` — там буде символьне посилання на `packages/contracts`. Правка в контракті видно у фронтенді миттєво, без публікації й перевстановлення.

### 9.2. Клієнт

`apps/web/src/api/client.ts`:

```ts
import createClient from "openapi-fetch";
import type { paths } from "@eventhub/contracts";

/**
 * Типізований клієнт API.
 *
 * createClient<paths> — тут і відбувається вся магія: з типу paths,
 * згенерованого зі специфікації, openapi-fetch виводить
 * дозволені шляхи, параметри запиту й типи відповідей.
 *
 * Наслідок: неіснуючий шлях або зайвий параметр — це помилка
 * компіляції, а не 404 у рантаймі.
 */
export const api = createClient<paths>({
  baseUrl: import.meta.env.VITE_API_URL,
});
```

Створіть **два** файли. Це окремий крок, а не довідка — без них фронтенд не отримає адресу API.

```bash
cat > apps/web/.env.example <<'EOF'
# Базовий URL API.
# 4010 — мок-сервер Prism; 3000 — справжній api-gateway (з тижня 2).
VITE_API_URL=http://127.0.0.1:4010
EOF

cp apps/web/.env.example apps/web/.env.local
```

- `.env.example` — **комітиться**, це список змінних зі значеннями-заглушками.
- `.env.local` — **не комітиться** (він у `.gitignore`), кожен створює його локально.

> **Перезапустіть dev-сервер після створення `.env.local`.** Vite читає цей файл лише при старті. Якщо сервер уже запущений, зміни не підхопляться.
>
> **Симптом, якщо файл забули.** `import.meta.env.VITE_API_URL` дорівнює `undefined`, `baseUrl` порожній, і запит іде відносно самого dev-сервера — на `localhost:5173/events`. Vite на невідомий шлях віддає `index.html` зі статусом **200**, тож у DevTools це виглядає як успішна відповідь. На сторінці при цьому просто нічого немає.
>
> Швидка перевірка: `console.log(import.meta.env.VITE_API_URL)` у `client.ts`.

> **Навіщо цей поділ.** `.env.example` — це список того, що потрібно для запуску, зі значеннями-заглушками. `.env.local` — реальні значення конкретної машини. У тижні 8 у другому файлі з'явиться ключ Stripe, і різниця стане критичною: ключ у публічному репозиторії живе до першого сканера, а це години, не дні.
>
> **Чому префікс `VITE_`.** Vite віддає клієнту лише змінні з цим префіксом. Це не примха, а захист: без префікса будь-яка змінна оточення, включно з паролем до бази, потрапила б у бандл, який відкриває будь-хто через DevTools.

### 9.3. Використання

`apps/web/src/features/catalog/EventList.tsx`:

```tsx
import { useEffect, useState } from "react";
import type { Event } from "@eventhub/contracts";
import { api } from "../../api/client";

export function EventList() {
  const [events, setEvents] = useState<Event[]>([]);
  const [problem, setProblem] = useState<string | null>(null);

  useEffect(() => {
    // openapi-fetch не кидає винятків на HTTP-помилках.
    // Замість цього повертає { data } АБО { error } — і TypeScript
    // не дасть звернутись до data, поки ви не перевірили error.
    // Це і є "помилки як частина контракту" з лекції.
    api
      .GET("/events", { params: { query: { limit: 20 } } })
      .then(({ data, error }) => {
        if (error) {
          // error має тип Problem — той самий, що описаний у специфікації
          setProblem(error.title);
          return;
        }
        setEvents(data.items);
      });
  }, []);

  if (problem) return <p role="alert">{problem}</p>;

  return (
    <ul className="event-list">
      {events.map((e) => (
        <li key={e.id}>
          <strong>{e.title}</strong> — {e.venue.city},{" "}
          {new Date(e.startsAt).toLocaleString("uk-UA")}
          {" · від "}
          {/* amount у копійках — ділимо на 100 лише для показу.
              У розрахунках копійки НІКОЛИ не перетворюються
              на дробові гривні. */}
          {(e.minPrice.amount / 100).toFixed(2)} грн
        </li>
      ))}
    </ul>
  );
}
```

### 9.5. Спостереження, заради якого варто зупинитись

Перевірте порожній стан. Тимчасово додайте заголовок у клієнт:

```ts
export const api = createClient<paths>({
  baseUrl: import.meta.env.VITE_API_URL,
  headers: { Prefer: "example=empty" },   // тимчасово, прибрати перед здачею
});
```

Ви побачите порожню сторінку без жодного пояснення. І — головне — вона виглядає **точно так само**, як сторінка під час завантаження.

Наш компонент розрізняє два стани: «є дані» і «помилка». Насправді їх щонайменше три: завантаження, порожньо, є результат. Два різні стани, показані однаково, — це не дрібниця верстки, а те, через що користувач тисне F5 на працюючому застосунку.

Мінімальне виправлення — одна змінна стану замість двох:

```tsx
type State =
  | { kind: "loading" }
  | { kind: "error"; message: string }
  | { kind: "ready"; events: Event[] };

const [state, setState] = useState<State>({ kind: "loading" });
```

Дискримінантне об'єднання тут не випендрювання: воно робить **неможливими** стани на кшталт «помилка й дані одночасно». Компілятор не дасть звернутися до `state.events`, поки ви не звузили тип перевіркою `state.kind === "ready"`.

Реалізувати це в межах лабораторної не обов'язково — але подивитись на порожню сторінку варто, бо в тижні 4 ми повернемось саме сюди. TanStack Query дає `isPending`, `isError` і `data` з коробки, і без сьогоднішнього спостереження це буде виглядати як зайва абстракція.

Не забудьте прибрати заголовок `Prefer` перед здачею.

> **Про `useEffect` із запитом.** Так робити в продакшні не варто: немає скасування запиту при розмонтуванні, немає кешу, немає повторних спроб, у StrictMode запит виконається двічі. У тижні 4 це все замінить TanStack Query. Зараз ми свідомо пишемо найпростіший варіант, щоб не змішувати дві нові теми в одному кроці.

### 9.6. Переконайтесь, що типи справді працюють

Проведіть три експерименти — це і є суть кроку. Після кожного поверніть код у робочий стан.

**1. Неіснуючий шлях.** Замініть `"/events"` на `"/evetns"`.
Компілятор має відхилити рядок: перелік допустимих шляхів походить зі специфікації, а не з довільних рядкових літералів.

**2. Неіснуюче поле.** Напишіть `e.venue.country`.
Помилка — такого поля в схемі `VenueSummary` немає.

**3. Зміна контракту змінює вимоги до коду.** Додайте `description` до `required` у схемі `Event`, виконайте `pnpm contracts`, потім приберіть назад і виконайте ще раз. Спостерігайте, як `e.description` то стає `string`, то повертається до `string | undefined`.

Третій експеримент найважливіший: **зміна одного рядка в YAML негайно змінила вимоги до коду фронтенду**. Саме за це ми платимо дисципліною design-first — і саме цього неможливо отримати, якщо типи писати руками.

### 9.7. Дослід Б: радіус ураження зміни контракту

Тепер граф залежностей повний: `web` залежить від `contracts`, `contracts` не залежить ні від кого. Можна порівняти з дослідом А з кроку 1.

```bash
pnpm build          # прогрів кешу
```

Тепер додайте в кінець `packages/contracts/openapi.yaml` рядок-коментар:

```yaml
# тест кешу
```

і зберіть ще раз:

```bash
pnpm build
```

Цього разу перезберуться **`contracts` і всі, хто від нього залежить** — тобто ще й `web`. Одна зміна в YAML тягне перевірку всього, що на цей контракт спирається.

У цьому й полягає різниця між дослідами:

| Що змінили | Що перезібралось | Чому |
|---|---|---|
| `apps/web/src/App.tsx` | лише `web` | від `web` не залежить ніхто |
| `packages/contracts/openapi.yaml` | `contracts` **і** `web` | `web` оголосив залежність від `contracts` |

Контракт — вершина графа, і кеш це чесно відображає. Саме тому в тижні 13, коли з'явиться CI, зміна однієї схеми автоматично запустить тести всіх її споживачів, а зміна стилів — нічого зайвого.

> **Питання рев'юверу.** Якби в `contracts` задача називалася `generate` замість `build` (див. розділ 5.3), який із двох дослідів дав би неправильний результат — і чому цю помилку важко помітити?

Приберіть тестовий коментар із `openapi.yaml` перед здачею.

### Контрольна точка 5

Два термінали, обидва **з кореня репозиторію**:

```bash
# термінал 1 — мок-сервер
pnpm mock
```

```bash
# термінал 2 — фронтенд
pnpm --filter web dev
```

`api-gateway` запускати не треба — до тижня 2 він не бере участі.

**Куди дивитись у браузері:**

| Порт | Що це | Коли відкривати |
|---|---|---|
| **5173** | сам застосунок | це і є ваш сайт |
| 4010 | мок-API, віддає JSON | лише для діагностики |

Фронтенд на 5173 сам звертається до 4010 у фоні — запит видно в DevTools → Network. Відкривати 4010 як сторінку не треба.

У браузері на `http://localhost:5173` видно список подій із даних мок-сервера. **Бекенд при цьому не запущений взагалі** — і в цьому вся суть кроку.

## 10. Крок 6. ADR-001

Скопіюйте `docs/adr/0000-template.md` у `docs/adr/0001-cursor-pagination.md` і заповніть.

Тема: **чому в каталозі курсорна пагінація, а не offset**.

Мінімальні вимоги до змісту:

- **Контекст.** Опишіть конкретну проблему вашого домену, а не загальні слова. Що саме відбувається, коли організатор додає подію між двома запитами користувача? Наведіть послідовність дій.
- **Розглянуті варіанти.** Щонайменше два, з чесним описом кожного. Варіант, який ви відкинули, має бути описаний так, щоб його прибічник упізнав свою позицію.
- **Рішення.** Одне-два речення, конкретно: за якими полями будується курсор і чому саме за ними. Підказка: чому одного `startsAt` замало?
- **Наслідки.** Обов'язково і плюси, і мінуси.

Мінуси, які варто згадати чесно: неможливість переходу «на сторінку 7», відсутність загальної кількості сторінок, складніший запит до БД, потреба у стабільному вторинному ключі сортування.

> **Чому розділ із мінусами обов'язковий.** ADR пишеться для майбутнього вас — людини, яка через півроку спитає «чому тут так незручно зроблено». Якщо в документі самі плюси, ця людина вирішить, що рішення було помилкою, і перепише. Чесний список мінусів каже: ми знали, ми заплатили свідомо, ось за що.

### Контрольна точка 6

Рев'ювер читає ADR і має бути здатним переказати рішення своїми словами, не заглядаючи в код.

## 12. Критерії приймання

Робота приймається, якщо виконано **всі** пункти.

| № | Критерій | Як перевіряється |
|---|---|---|
| 1 | Чистий клон запускається за інструкцією з README | Рев'ювер із іншої команди клонує репо в порожню папку |

## 13. Типові проблеми

**`ERR_PNPM_WORKSPACE_PKG_NOT_FOUND`**
`pnpm-workspace.yaml` лежить не в корені або шаблони в ньому не покривають вашу папку. Перевірте, що файл у корені та містить `packages/*` і `apps/*`.

**Turborepo не кешує, щоразу перезбирає**
Для задачі не задані `outputs` у `turbo.json`, або в задачі є недетермінований вхід — наприклад, поточна дата, що потрапляє у збірку.

**Зміна `openapi.yaml` не інвалідує фронтенд**
У пакеті `contracts` задача називається не `build`. Тоді `^build` у `web` не знаходить її, ребро графа не утворюється — див. розділ 5.3.

**curl показує `0` отриманих байтів і жодної помилки**

Відповіді не було взагалі — це не «прийшла порожня». Дві найчастіші причини:

1. **Кирилиця в рядку запиту.** Використовуйте `-G --data-urlencode "city=Вінниця"` замість `?city=Вінниця`.
2. **`localhost` резолвиться в IPv6.** Пишіть `127.0.0.1` явно.

Додавайте `-i` до кожного діагностичного запиту: без нього ви не відрізните 404 з порожнім тілом від невстановленого з'єднання.

**`curl: (7) Failed to connect`**
Prism не запущений або впав при старті. Подивіться в його термінал: при успішному старті він друкує список змонтованих маршрутів.

**Фільтр `?city=…` не фільтрує — відповідь завжди однакова**
Так і має бути. Prism не має бізнес-логіки: він віддає приклад із контракту незалежно від параметрів. Фільтрація з'явиться в тижні 2 разом із бекендом. Див. «Що Prism робить і чого не робить» вище.

**Prism віддає `"string"` замість нормальних даних**
Немає прикладів. Додайте `examples` на рівні Media Type (мапа імен → `value`) або запустіть Prism із `--dynamic`, щоб він генерував випадкові дані за схемою.

**Swagger Editor: `property "example" is deprecated, use "examples" instead`**
Усередині схеми ключ однини застарів: у OpenAPI 3.1 схеми — це JSON Schema 2020-12, де ключове слово називається `examples`. Просто перейменувати замало — воно приймає **масив**, інакше отримаєте `examples must be an array`. Детально — у розділі 6.3.

**Помилка CORS у браузері**
Prism дозволяє CORS за замовчуванням. Якщо помилка є — ви звертаєтесь не на порт 4010. Перевірте `VITE_API_URL` і що `.env.local` створено. Vite читає цей файл лише при старті, тому після зміни перезапустіть dev-сервер.

**Сторінка відкривається, але список подій порожній, помилок немає**
Найімовірніше немає `apps/web/.env.local`. Тоді `baseUrl` порожній, запит іде на `localhost:5173/events`, Vite віддає `index.html` зі статусом 200 — і все виглядає «успішно». Перевірте: `ls apps/web/.env.local`, далі `console.log(import.meta.env.VITE_API_URL)`.

Друга можлива причина: у клієнті лишився тимчасовий заголовок `Prefer: example=empty` із розділу 9.5.

**Vite не бачить змінну оточення**
Або немає префікса `VITE_`, або файл називається не `.env.local`, або dev-сервер не перезапущено після його створення.

**TypeScript не бачить `@eventhub/contracts`**
Виконайте `pnpm install` у корені після додавання залежності. Якщо не допомогло — перезапустіть TS-сервер у редакторі (VS Code: `Ctrl+Shift+P` → *TypeScript: Restart TS Server*). Ще одна причина: ви не виконали `pnpm contracts`, тому `src/generated/schema.d.ts` просто не існує.

**`unmet peer typescript@">=4.8.4 <6.1.0": found 7.0.2`**
`typescript-eslint` оголошує `typescript` як peer-залежність. Якщо в пакеті, де він використовується, немає власного оголошення `typescript`, pnpm доставляє peer сам — і бере найновіший, тобто TypeScript 7 (нативний порт на Go). Впізнати легко: pnpm завантажує бінарник `@typescript/typescript-win32-x64` близько 10 МБ, якого ви не просили.

Ліки — додати `"typescript": "5.9.3"` у `devDependencies` того пакета (у `packages/config` це вже зроблено), потім `pnpm install`.

**`ERR_PNPM_IGNORED_BUILDS` або `Ignored build scripts: esbuild`**
Пакет зі скриптом встановлення не розглянутий. Додайте його в `allowBuilds` у `pnpm-workspace.yaml` зі значенням `true` або `false` і перевстановіть. Для `esbuild` потрібне `true` — без нього не працює збірка Vite.

**`ERR_PNPM_UNSUPPORTED_ENGINE ... Your Node version is incompatible with "<шлях до проєкту>"`**
У повідомленні названо шлях до вашого проєкту — отже, у вас Node не з дозволеної LTS-лінії. Перемкніться на 24 за таблицею з розділу 2.

На Windows найчастіша причина того, що «перемкнув, а не допомогло»: nvm-windows не читає `.nvmrc`, тому `nvm use` без аргументу мовчки нічого не робить. Перевіряйте результат через `node -v`, а не через відсутність помилки.

**`ERR_PNPM_UNSUPPORTED_ENGINE`, але назване не ваш проєкт, а якийсь пакет**

Приклад:

```
This error happened while installing a direct dependency of ...
Your Node version is incompatible with "@stoplight/prism-cli@5.16.0".
Expected version: >=24.18.0
Got: v24.10.0
```

`engineStrict` перевіряє `engines` і в залежностях теж. Тут ваша версія Node задовольняє `engines` проєкту, але не задовольняє вимогу пакета. Читайте рядок `Expected version` — він каже, що саме поставити.

Якщо вимога пакета несумісна з тим, що записано в `engines` проєкту (наприклад, залежність хоче Node 26, а проєкт дозволяє лише 24), самотужки це не розв'язується — повідомте викладача.

**`The "pnpm" field in package.json is no longer read by pnpm`**
Ви користуєтесь інструкцією, написаною для pnpm 10. Перенесіть налаштування в `pnpm-workspace.yaml`; `onlyBuiltDependencies` там називається `allowBuilds` і має інший формат — мапа `пакет: true|false` замість списку. Автоматично: `pnpx codemod run pnpm-v10-to-v11`.

**`Command "mock" not found` / `ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL`**
Ви в підпапці. Перейдіть у корінь репозиторію або використайте `pnpm -w mock`.

**`openapi-typescript` падає з помилкою парсингу YAML**
Найчастіше — відступи. У YAML вкладеність визначається пробілами, табуляція заборонена. Перевірте специфікацію в Swagger Editor: він показує рядок із помилкою.

## 15. Домашнє завдання

Описати в тій самій специфікації ендпоїнти замовлень: створення, перегляд, скасування.

Для кожної помилки, яку може повернути API, оберіть код статусу, додайте іменований приклад відповіді й **письмово обґрунтуйте** вибір коду в коментарі YAML. Окремо продумайте:

- яку відповідь поверне API, якщо місце вже утримує інший покупець;
- яку — якщо подія скасована організатором;
- яку — якщо користувач намагається скасувати чуже замовлення;
- чим по суті відрізняються ці три випадки з погляду клієнта.

> **Підказка до останнього пункту.** Запитайте себе для кожного випадку: чи має сенс повторити той самий запит через хвилину? Відповідь на це питання і визначає код статусу.

Реалізовувати нічого не треба — лише контракт. У тижні 7 ви побачите, наскільки точно вгадали.
