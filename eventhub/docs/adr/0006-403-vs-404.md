# ADR-0006: коли 403, а коли 404

## Статус

Прийнято · 2026-10-29

## Контекст

У роботі 6 з'явився третій рівень перевірки прав - власність на запис
(`organizerId` у `Event`, `userId` у `Order`). До цього моменту коди
помилок вибирались по одному, без явного правила: `GET /orders/{orderId}`
уже повертав 404 на чуже замовлення (робота 2-3, домашнє завдання),
`POST /organizer/events` - 403 на чужу роль (`RolesGuard`), а
`PATCH /organizer/events/{eventId}` - знову 404 на чужу подію.

Без явного правила кожен новий ендпоїнт обирає код навмання, і рев'юер
не має критерію, за яким це перевірити. Потрібне одне правило для
всього API EventHub, а не рішення для кожного випадку окремо.

## Розглянуті варіанти

### Варіант A. 403 завжди, коли користувач автентифікований, але дію заборонено

- Плюси: простіше для клієнта - одна й та сама причина («не можу»)
  завжди повертає один код, незалежно від того, йде мова про роль чи
  про власність.
- Мінуси: 403 на чужий запис підтверджує факт його існування. Організатор
  А, перебираючи `eventId`, за кодом 403 проти 404 дізнається, які
  ідентифікатори належать організатору Б, навіть не бачачи вмісту
  запису. Для публічних сутностей (роль на маршруті) це не проблема -
  маршрут `/organizer/events` і так ні для кого не секрет.

### Варіант B. Правило за рівнем перевірки (обрано)

- 401 - рівень 1, «хто ви» (немає/недійсний access-токен).
- 403 - рівень 2, «вашій ролі заборонено сам маршрут», коли дозвіл
  не залежить від конкретного запису, а від того, хто ви в принципі
  (роль). Факт існування маршруту й так публічний - приховувати нічого.
- 404 - рівень 3, «цей конкретний запис», коли дозвіл залежить від
  того, чий це запис. Якби сервер повертав тут 403, запит одночасно
  підтверджував би й «запис існує», і «він не ваш» - для зловмисника
  це двічі корисніше, ніж один 404, який не каже нічого.
- Плюси: не підтверджує існування чужих записів (головна перевірка
  роботи 6, розділ 6.5 методички); правило одне, і кожен новий
  ендпоїнт перевіряється за ним без окремого рішення.
- Мінуси: клієнту (і людині, що читає логи) 404 «не знайдено» і 404
  «чуже» виглядають однаково - для діагностики своїх власних помилок
  розробник бачить менше деталей, ніж при явному 403. Узгоджено
  навмисно: деталь, корисна чесному розробнику при налагодженні,
  рівно так само корисна зловмиснику при розвідці.

## Рішення

Код помилки визначається рівнем перевірки, яка не пройшла, а не типом
дії:

| Рівень | Питання | Приклад | Код |
|---|---|---|---|
| 1 | Чи ви увійшли? | Відсутній/недійсний access-токен | 401 |
| 2 | Чи дозволено вашій ролі сам маршрут? | `USER` на `/organizer/events` | 403 |
| 3 | Чи ваш це конкретний запис? | Чужа подія, чуже замовлення | 404 |

Перевірка для нового ендпоїнта: чи залежить відмова від *якого саме*
запису йде мова (а не лише від ролі запитувача)? Якщо так - 404, і
перевірка власності йде умовою в `WHERE` запиту до бази (`updateMany`/
`findFirst` зі скоупом), а не окремим `if` після читання запису.
Якщо відмова однакова для будь-якого запису цього типу (маршрут
узагалі не для цієї ролі) - 403.

## Наслідки

**Позитивні**

- Один критерій для всього API: рев'юер перевіряє новий ендпоїнт за
  таблицею вище, а не вгадує.
- Чужий запис невідрізнимий від неіснуючого в усіх відповідях API
  (`GET /orders/{orderId}`, `PATCH /organizer/events/{eventId}`) -
  розвідка через коди відповіді не працює.

**Негативні й компроміси**

- Організатор, що помилився в `eventId` (і просто не вгадав), і
  організатор, що намагається редагувати чужу подію, отримують
  однакову відповідь. Відрізнити ці два випадки з відповіді неможливо
  навмисно - це ціна, яку плачено за відсутність розвідки.
- Правило працює, доки перевірка власності живе в запиті до бази
  (`WHERE organizerId: …`). Якщо хтось повернеться до варіанта
  «прочитати запис, потім порівняти `organizerId` в `if`» (методичка
  ЛР6, 6.3, варіант «як не слід робити») - вікно між читанням і
  записом лишається, а 404 перетворюється на правильний код over
  неправильну реалізацію.

**Що доведеться переглянути, якщо…**

- з'явиться потреба показати користувачу, *чому* саме відмовлено
  (наприклад, окрема сторінка «у вас немає доступу» замість generic
  404) - тоді 404 для рівня 3 доведеться або лишити як є в API і
  додати пояснення тільки в UI (не видаючи його через код відповіді),
  або усвідомлено прийняти ризик розвідки для цього конкретного
  ендпоїнта;
- з'явиться потреба в аудиті спроб доступу до чужих записів для
  виявлення зловживань (так само, як лог `refresh token reuse
  detected` у роботі 5) - тоді 404 у відповіді лишається, а різниця
  між «не існує» і «чуже» фіксується окремо в логах сервера, не в
  HTTP-відповіді.
