# Архітектурні рішення (ADR)

Кожне рішення, яке потім буде дорого змінити, фіксується окремим документом.

## Правила

1. **Один файл — одне рішення.** Нумерація наскрізна: `0001-`, `0002-`, …
2. **Файл не редагується після прийняття.** Передумали — новий ADR зі статусом
   «замінює ADR-XXXX». Історія рішень має зберігатися.
3. **Розділ «Наслідки» обов'язковий, і мінуси в ньому обов'язкові.**
   Документ без мінусів — це реклама, а не рішення. Рев'ювер має право
   не прийняти PR з таким ADR.
4. **Пишеться до реалізації, а не після.** Якщо ADR з'явився після коду —
   це вже не рішення, а виправдання.

## Що заслуговує на ADR

Питання, у якому був реальний вибір і де варіант, що програв, теж мав сенс.

| Заслуговує | Не заслуговує |
|---|---|
| Курсорна пагінація замість offset | Назва змінної |
| JWT у httpOnly-cookie замість localStorage | Порядок імпортів |
| Розпил моноліту на сервіси | Вибір бібліотеки іконок |
| Монорепо замість кількох репозиторіїв | Відступ у два пробіли |

|---|---|---|
