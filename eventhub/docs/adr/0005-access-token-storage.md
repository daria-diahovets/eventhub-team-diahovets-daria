# ADR-0005: де зберігати access-токен на фронтенді

## Статус

Прийнято · 2026-10-12

## Контекст

У роботі 5 бекенд видає пару токенів: refresh - у httpOnly-cookie (JavaScript
до нього доступу не має, це закрито окремим ADR-рівня рішенням самої
методички), і access - у тілі відповіді `/auth/login` та `/auth/refresh`.
Фронтенд має десь зберегти саме access-токен між рендерами React і
перечитувати його на кожен запит через `authFetch`.

На відміну від refresh-токена, access-токен короткоживучий (15 хвилин,
`JWT_ACCESS_TTL_SECONDS`), і сам факт його витоку через XSS - менш
катастрофічний, ніж витік refresh-токена: зловмисник отримає максимум
15 хвилин доступу, а не можливість нескінченно подовжувати сесію. Але
"менш катастрофічний" не означає "неважливий", тому вибір місця
зберігання все одно вимагає явного рішення, а не браузерної звички
"кладемо все в localStorage".

## Розглянуті варіанти

### Варіант A. `localStorage`

- Плюси: переживає перезавантаження сторінки без додаткового коду,
  синхронізується між вкладками "безкоштовно" (подія `storage`).
- Мінуси: будь-який скрипт на сторінці має доступ через
  `localStorage.getItem`. Будь-яка XSS-вразливість (навіть у залежності
  третьої сторони, підключеній на сторінку) читає токен напряму.
  Це саме той ризик, який методичка прямо називає неприйнятним для
  refresh-токена; для access-токена ризик менший за наслідками, але
  вектор атаки - той самий.

### Варіант B. `sessionStorage`

- Плюси: ті самі переваги, що в `localStorage` (переживає F5), але
  зникає із закриттям вкладки - трохи менше вікно ризику.
- Мінуси: той самий вектор атаки через XSS, що й у варіанті A -
  JavaScript на сторінці однаково має прямий доступ через
  `sessionStorage.getItem`. Не розв'язує головну проблему, лише
  скорочує час, протягом якого вона існує.

### Варіант C. Змінна модуля (пам'ять), обрано

- Плюси: жоден API браузера (`localStorage`, `document.cookie`,
  DevTools → Application) не бачить токен як підписану сутність -
  його можна прочитати лише виконавши довільний JS у тому самому
  контексті виконання, що й сам застосунок, тобто дістати його не
  простіше, ніж дістати будь-яку іншу змінну в пам'яті сторінки.
  Токен зникає сам собою при закритті чи перезавантаженні вкладки -
  не потрібно окремого коду для "забути токен".
- Мінуси: саме тому, що токен зникає при F5, потрібен додатковий
  механізм відновлення сесії (мовчазний `refreshAccessToken()` при
  старті застосунку, крок 9.3 методички) - без нього кожне
  перезавантаження сторінки виглядало б як вихід з системи. Не
  синхронізується між вкладками автоматично (див. нижче).

### Варіант D. Access-токен теж у httpOnly-cookie

- Плюси: той самий захист від XSS, що й у refresh-токена.
- Мінуси: тоді кожен запит на будь-який маршрут автоматично нести
  б access-токен, включно з маршрутами, де він не потрібен, і
  JwtAuthGuard довелось би читати з `req.cookies`, а не з заголовка
  `Authorization` - це ламає явне розмежування методички між "secret,
  яким сервер керує сам" (refresh, cookie) і "токен, яким явно керує
  клієнтський код запиту" (access, заголовок). Ускладнює CORS і не
  дає жодної практичної переваги над варіантом C для токена, що й так
  живе лише 15 хвилин.

## Рішення

Access-токен зберігається у звичайній змінній модуля
(`apps/web/src/api/authToken.ts`, `getAccessToken`/`setAccessToken`) -
варіант C. Жодного API браузера, здатного віддати токен довільному
скрипту на сторінці через читання сховища, не використано.

## Наслідки

**Позитивні**

- Поверхня атаки для крадіжки access-токена через XSS не більша за
  поверхню атаки на будь-яку іншу змінну застосунку - немає окремого
  "сховища", яке варто спеціально шукати.
- Не потрібен код для очищення токена при виході чи закритті вкладки -
  пам'ять звільняється сама.

**Негативні й компроміси**

- Кожне перезавантаження сторінки вимагає мовчазного `POST /auth/refresh`
  до того, як застосунок дізнається, що користувач уже увійшов - зайвий
  мережевий виклик на кожен F5 (виправдано: дешевше за альтернативу
  зі сховищем, яке читає XSS).
- Немає "безкоштовної" синхронізації між вкладками: кожна вкладка має
  власну копію змінної модуля. Два відкриті вкладки після входу в одній
  з них не бачать входу одна в одній, поки кожна сама не звернеться
  до `/auth/refresh` (природно відбувається при першому запиту в
  іншій вкладці, але не миттєво).

**Що доведеться переглянути, якщо…**

- знадобиться справжня синхронізація сесії між вкладками в реальному
  часі (вихід в одній вкладці одразу розлогінює іншу, без очікування
  наступного запиту) - тоді додається `BroadcastChannel` або
  `storage`-подія на допоміжний прапорець (не сам токен!) у
  `localStorage`, що лише сигналізує іншим вкладкам "токен застарів,
  зроби власний refresh", а не передає сам секрет;
- access-токен доведеться різко подовжити (наприклад, для офлайн-режиму) -
  тоді ризик від XSS за варіантом C зростає пропорційно часу життя
  токена, і варто повернутися до обговорення варіанту D всупереч
  поточному висновку.
