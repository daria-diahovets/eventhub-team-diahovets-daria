# EventHub

Навчальний проєкт курсу веб-технології та веб-дизайн: портал продажу квитків на події (EventHub).

Це **стартовий стан тижня 1**. В роботі не вистачає частини каркаса — який ви створите самостійно виконуючи дану лабораторну роботу № 1.

---

## Проєкт містить

```
eventhub/
├── apps/
│   ├── web/               React 19 + TypeScript + Vite (порожня заготовка)
│   └── api-gateway/       NestJS 11, єдиний ендпоїнт GET /health
├── packages/
│   └── config/            спільні tsconfig і eslint
└── docs/adr/              шаблон архітектурного рішення
```

### Також в стартовом наборі потрібно самостійно додати інші елементи для розробки проєкту

| Файл / папка                                                     | Крок лабораторної |
| ---------------------------------------------------------------- | ----------------- |
| `pnpm-workspace.yaml` (workspace, `allowBuilds`, `engineStrict`) | крок 1            |
| кореневий `package.json`                                         | крок 1            |
| `turbo.json`                                                     | крок 1            |
| `packages/contracts/` (OpenAPI + згенеровані типи)               | кроки 2–3         |
| `apps/web/.env.example` та `.env.local`                          | крок 5            |
| `docs/adr/0001-*.md`                                             | крок 6            |

Поки цих файлів немає, `pnpm install` у корені **не спрацює** — це очікувано.

## Як влаштований репозиторій

**`apps/`** — те, що **запускається**. Кожна папка має власний життєвий цикл,
власні залежності, а з тижня 12 — власний Dockerfile. Межі папок тут навмисно
збігаються з межами майбутніх сервісів: у тижні 10 моноліт розпилюється саме
по цих лініях.

**`packages/`** — те, що **імпортується**. Саме по собі не запускається ніколи.
Головне правило: граф залежностей спрямований від `apps/` до `packages/`
і ніколи навпаки.

**`packages/contracts`** (з'явиться на кроці 2) — вершина цього графа.
Від нього залежать усі, він не залежить ні від кого. Якщо колись захочеться
додати туди залежність на інший пакет — це сигнал, що в контракт кладуть
щось зайве.

**`docs/adr/`** — рішення, які потім буде дорого змінити. Пишуться **до**
реалізації. Правила — у `docs/adr/README.md`.

## Передумови

```bash
node --version    # v24.20.0 або новіше в лінії 24
pnpm --version    # 11.x
```

Версія Node не довільна: `@stoplight/prism-cli` вимагає щонайменше 24.18.0,
тому лінія 22 не підходить узагалі, а Current-гілка (25, 27) заборонена
в `engines`. Перевірка блокуюча — на невідповідній версії `pnpm install`
завершиться помилкою `ERR_PNPM_UNSUPPORTED_ENGINE`.

### Перемикання версії Node

У корені лежать `.nvmrc` і `.node-version` зі значенням `24.20.0`.

| Інструмент                  | Команда                                       | Читає файл версії |
| --------------------------- | --------------------------------------------- | ----------------- |
| fnm (рекомендовано, усі ОС) | `fnm install && fnm use`                      | так               |
| nvm (Linux, macOS)          | `nvm install && nvm use`                      | так               |
| Volta                       | перемикає сам                                 | так               |
| **nvm-windows**             | `nvm install 24.20.0`, далі `nvm use 24.20.0` | **ні**            |

nvm-windows не читає `.nvmrc` і вимагає повний номер версії. Якщо ви
на Windows, простіше поставити fnm:

```powershell
winget install Schniz.fnm
fnm install
fnm use
node -v          # перевірте результат, а не відсутність помилки
```

**Перевіряйте `node -v` після перемикання.** nvm-windows на `nvm use` без
аргументу мовчки нічого не робить, і легко піти далі на старій версії.

Якщо pnpm немає:

```bash
corepack enable
corepack prepare pnpm@latest --activate
```

Windows: працюйте у WSL2 або Git Bash і одразу виконайте
`git config --global core.autocrlf input`.

## Запуск (після виконання кроку 1 лабораторної)

```bash
pnpm install

# згенерувати типи зі специфікації
# (обов'язково після кожної зміни openapi.yaml)
pnpm contracts

# мок-сервер із контракту   → http://localhost:4010
pnpm mock

# фронтенд                  → http://localhost:5173
pnpm --filter web dev

# бекенд                    → http://localhost:3000/health
pnpm --filter api-gateway dev
```

Фронтенд і бекенд запускаються **незалежно**. До тижня 2 `web` працює проти
мок-сервера Prism, а не проти `api-gateway` — у цьому й полягає сенс
підходу design-first.

## Перевірка бекенду

```bash
curl http://localhost:3000/health
# {"status":"ok","uptime":3.12,"version":"0.1.0"}
```

## VS Code

У репозиторії є `.vscode/settings.json` — він застосовується автоматично
при відкритті папки проєкту. Нічого налаштовувати вручну не треба.

Що він робить:

- **робить Git Bash терміналом за замовчуванням на Windows** — усі команди
  методички написані під Bash;
- **вмикає TypeScript із `node_modules`**, а не вбудований у VS Code, щоб
  редактор показував ті самі помилки, що й `pnpm typecheck`;
- ставить LF, форматування при збереженні й автовиправлення ESLint;
- виключає `node_modules` і `dist` з індексації, інакше пошук по монорепо
  стає марним.

При першому відкритті VS Code запропонує встановити рекомендовані розширення
(`.vscode/extensions.json`) — погодьтесь. Серед них розширення для OpenAPI:
воно підсвічує помилки в `openapi.yaml` прямо в редакторі.

> Якщо після відкриття проєкту в рядку стану видно версію TypeScript,
> відмінну від 5.9.3 — натисніть на неї та оберіть **Use Workspace Version**.
